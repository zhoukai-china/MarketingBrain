# 人设生成引擎 · 子模块规格（Module B）

> 所属：商户测试团 · 视频测试智能体
> 定位：模块 B（上游接 A/目标用户解析，下游供 D/代入推理）
> 状态：WorkBuddy 原型规格（非生产代码），供技术合伙人直接工程化
> 平台：思潼 AI（模型默认 DeepSeek 经阿里百炼）

---

## 1. 文档目的

把"用户输目标用户 → 自动批量生成虚拟观众"这一步做成**独立、可调用、可复现**的子能力。它是整个产品的差异化引擎（世界观 skill 的工程化形态），不是写死的 5 个角色。

---

## 2. 输入契约（来自 Module A 的结构化 Brief）

| 字段 | 类型 | 必填 | 说明 |
|------|------|:---:|------|
| industry | string | ✅ | 行业，如 餐饮/美业/实业/大健康/招商/教培 |
| region | string | ❌ | 地域，影响方言与消费习惯 |
| scale | string | ❌ | 企业规模，如 夫妻店/单店/连锁3-10家/10家以上 |
| decision_maker | object | ❌ | 决策者：{age, gender, education, background} |
| pain_points | string[] | ✅ | 核心痛点列表（至少 1 个） |
| decision_style | string | ❌ | 主导决策风格关键词 |
| count | int | ❌ | 生成人数，默认 5，范围 3–7 |
| focus_axis | string | ❌ | 重点拉开差异的维度（如"价格敏感度"） |
| seed_personas | object[] | ❌ | 用户自有客户画像，作为生成种子 |

**自由文本兜底**：若 Module A 只收到自由文本，需先解析为上述结构。解析失败则向用户追问缺失必填项（industry / pain_points / count）。

---

## 3. 输出契约（Persona Schema + 示例）

每位人设必须包含以下字段，存入**人设注册表（Persona Registry）**：

```json
{
  "id": "P_20260926_a3f1",
  "name": "老周",
  "title": "餐饮连锁创始人",
  "dimension_tags": {            // 用于维度正交校验，必须填
    "decision_style": "结果导向",
    "price_sensitivity": "中",
    "trust_threshold": "高",
    "digital_level": "低",
    "risk_appetite": "中"
  },
  "physiology": "46岁男，微胖，发际线后移，手指被烟熏黄",
  "sociology": "初中毕业白手起家，年营收千万级，管几十人",
  "psychology": "急性子、认结果不认理论、对新媒体半信半疑",
  "core": {
    "trait_3": ["实在","急性子","嘴硬"],
    "desire": "多开新店、天天有客资",
    "fear": "被割韭菜、花冤枉钱",
    "lie": "拍视频是年轻人瞎折腾，我实干的不适合"
  },
  "voice": {                     // 声线卡，防 OOC 关键
    "catchwords": ["扯淡","整那没用的","你跟我说人话"],
    "sentence": "东北短句、直来直去",
    "metaphor": "生意/过日子类",
    "taboo": ["绝不承认不懂","不说专业术语"]
  },
  "criteria": [                  // 评判视频的标准，用于 Module D
    "能不能大白话讲清对我开店有啥用",
    "有没有真实案例和数，不是PPT概念",
    "是不是又在变着法卖课"
  ],
  "stance": "能让我多来客资多开两家店，我就服"
}
```

**输出格式**：`personas: Persona[]`（数组，长度=count）+ `registry_id`（便于同 Brief 二次测试比对）。

## 4. 生成管线（实现流程）

```
Step 1  解析 Brief
        └─ 提取正交维度轴（见第5节），若 focus_axis 指定则优先该轴
Step 2  维度正交分配（代码层，非 LLM）
        └─ 对 count 个人，在主导轴上轮询分配互斥取值，保证签名不重复
Step 3  模板匹配（可选）
        └─ 命中行业预设 archetype 则载入底稿，否则走通用底稿
Step 4  LLM 填充细节（两步合一调用）
        └─ 按"生成提示词模板"产出 三维 + 声线卡 + 评判标准 + 立场
        └─ 若 seed_personas 有值，注入其特质做混合
Step 5  一致性校验
        └─ 声纹不串（口癖互不重叠）、不 OOC、criteria 与身份自洽
        └─ 维度正交校验（任意两人 dimension_tags 签名不完全相同）
Step 6  注册表落盘
        └─ 生成稳定 id（见第6节），写思潼存储，返回 registry_id
```

> 建议**两阶段实现**：Step 2（控轴）+ Step 5（校验）用代码 deterministic 执行；Step 4（填细节）用一次 LLM 调用批量产出 count 个。这样既可控又省 token。

---

## 5. 维度正交机制（防同质化核心）

定义 5 条正交轴，批量生成时强制拉开：

| 轴 | 取值样例 | 作用 |
|----|---------|------|
| decision_style 决策风格 | 结果导向 / 怕被坑 / 面子型 / 合规型 / 价格敏感 | 主导差异轴 |
| price_sensitivity 价格敏感 | 高 / 中 / 低 | 影响对"付费/定价"类内容的反应 |
| trust_threshold 信任门槛 | 高 / 中 / 低 | 影响"割韭菜"判定 |
| digital_level 数字化程度 | 高 / 中 / 低 | 影响对"AI/系统"的接受度 |
| risk_appetite 风险偏好 | 高 / 中 / 低 | 影响尝试意愿 |

**分配算法**：
1. 以 `decision_style` 为主轴，count 个人轮流取不同值（如 5 人→结果导向/怕被坑/面子型/合规型/价格敏感 各一）。
2. 其余轴在 ±1 档内随机但互斥，避免两人签名完全相同。
3. 若 `focus_axis` 指定（如"价格敏感度"），则该轴升为主轴优先拉开。
4. 校验：任意两人 `dimension_tags` 全文相似度 < 阈值（如完全相同则扰动重排）。

**目的**：保证生成出来的 N 个人"像不同真实客户"，而不是同一个模板换名字——否则视频测试失去意义（都只代表一种立场）。

---

## 6. 可复现机制

- **稳定 id**：`P_{日期}_{Brief哈希前4位}_{序号}`，相同 Brief 产出相同 id 序列。
- **种子固定**：LLM 调用携带 `seed = hash(Brief + index)`，相同输入相同输出（思潼/百炼需支持 seed 参数；不支持则用 temperature=0 + 固定 few-shot 近似）。
- **注册表缓存**：同一 `registry_id` 二次测试直接复用，不重新生成，保证跨轮对比有效。

---

## 7. 生成系统提示词模板（Module B 专用）

```
你是人设生成引擎。给定目标用户 Brief，生成 {count} 个虚拟观众，用于短视频代入测试。

【约束】
- 每人严格符合 Egri 三维(生理/社会/心理) + 声线卡(口癖/句式/比喻/禁忌) + 评判标准 + 立场
- 5 条正交轴(decision_style/price_sensitivity/trust_threshold/digital_level/risk_appetite)
  必须拉开差异，任意两人签名不得完全相同
- 声线卡口癖在批次内互不重叠，遮名可辨是谁在说话
- 评判标准必须与其身份/痛点自洽，不写无关项
- 不编造行业不存在的痛点；region 影响方言与习惯

【输入 Brief】
{structured_brief}

【输出】严格 JSON 数组，字段见 Persona Schema，含 dimension_tags 与 voice
```

## 8. 质量验收（Module B 自测项）

- [ ] 同 Brief 多次生成 → persona 签名稳定（可复现）
- [ ] 任意两人 dimension_tags 不完全相同（正交通过）
- [ ] 批次内口癖互不重叠，遮名能分辨说话人（声纹通过）
- [ ] 每人 criteria 与身份/痛点自洽（不 OOC）
- [ ] count 越界（<3 或 >7）自动夹取并提示
- [ ] 缺必填项（industry/pain_points）返回明确追问，不静默生成
- [ ] seed_personas 注入后，产出体现种子特质

---

## 9. 与上下游接口

| 接口 | 方向 | 数据 |
|------|------|------|
| A → B | 入 | 结构化 Brief（第2节） |
| B → D | 出 | personas[] + registry_id（第3节） |
| B ↔ 存储 | 存 | 人设注册表（思潼存储，registry_id 索引） |

---

## 10. 成本估算（参考）

- 单次生成 = 1 次 LLM 调用（输出 count×~600 token ≈ 3–4k token），远低于视频理解（多模态图 + 长 transcript）。
- 建议定价中"人设生成"成本可忽略，主要成本在 Module C/D 的视频理解。
- 注册表缓存命中时，二次测试 B 模块零成本。

---

## 11. 红线（必须写入实现）

- ❌ 不编造行业/画像不存在的痛点或能力
- ❌ 生成内容不得含平台违规引导语（本模块只产人设，但 criteria/stance 不得夹带"私信/找我"类）
- ❌ 不替用户决定行业——industry 缺失必须追问，不默认
