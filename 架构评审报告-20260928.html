一、总体判断

这是一套业务能力跑得很快、工程地基没跟上的系统。产品侧堆出了 5 条产品线 + 商城 + 知识库， 后端 119 个 service、前端 45 个页面；但支撑这些的地基件——队列、缓存、请求层、状态管理、CI、测试、限流、可观测性——几乎全部缺席或半成品。 好消息是：钱相关的部分（计费预留、幂等、租户身份解析）写得相当扎实，说明团队有能力写好代码，只是没把这套标准推到全局。

先说做得好的（这些别动）

· 预留—执行—结算三段式计费：credit-reservations.ts 事务预留 + 幂等退款键 ${reservationId}#release，失败不多退、重复不双倍退。设计质量高于同类系统平均水平。

· 租户身份解析 fail-closed：request-context.ts 只信验签后的 JWT payload，裸 header 仅在 OPS 通道且 timingSafeEqual 常量时间比对；未配 OPS_TOKEN 直接关闭旁门。曾经的 identity spoof 漏洞修得很干净。

· 环境变量 zod 强校验 + 启动期跨字段二次校验（parse 而非 safeParse），配置缺失直接拒启动，不静默降级。硬编码密钥 0 处。

· MCP 调用有熔断（mcp-client.ts 的 circuitOpenUntil + cooldown）——说明团队知道熔断怎么写，只是没覆盖到 LLM。

· 资金路径刻意用 Serializable，且 P2034 冲突重试在两处有正确实现；64 处事务体内没有混入 LLM/HTTP 调用（这点很多团队都做不到）。

· 前端 45 个页面级 lazy() 全量代码分割，首屏可控。

三、P0：现在就该处理的

① 长任务同步阻塞 + 零队列 —— 最大的架构性风险

生成类任务在 HTTP 请求线程里同步跑。直播话术是 9 段 + 1 附属件串行 10 次模型调用，实测一单约 6.5 分钟。这期间客户端必须死等连接，nginx 或浏览器任一超时就前功尽弃，且已花掉的 9 次模型成本全额沉没。项目里已经发生过一次：重启打断长任务 → 502。

图 2 · 长任务链路：现状 vs 应为

② 数据库迁移已漂移，且代码在运行时执行 DDL

这是最容易被忽视、但迟早会炸的一类问题。实测确认：

  • migration_lock.toml 不存在（57 个迁移目录，无 provider 锁）；
  • schema 里有的 TopicStagedMaterialSelection，在全部 57 个 migration.sql 里 0 命中 —— 已经漂移；
  • marketplace.ts 在请求处理路径里执行 CREATE TABLE IF NOT EXISTS / ALTER TABLE ... ADD COLUMN（1382 / 1396 / 1482 行），等于让应用代码隐式改库结构；
  • 生产走 prisma migrate deploy（正确），但仓库里 没有 drift 检测，且验收脚本里有直接 db push 的。

风险闭环：只要本地有人跑过 db push 或运行时 DDL 先建了表，下次 migrate deploy 遇同名 CREATE 会失败或静默不一致——而且是在发布当天才发现。

③ 数据层租户隔离没有兜底

身份解析层写得很好，但往下走一层就没了：Prisma 无 $extends、无 middleware、无 RLS，100% 靠开发者手写 where: { tenantId }。抽样发现 114 处按 id 直接定位、语句内不带 tenantId 的访问点（offlineEvent、marketplaceSubscription、desktopDevice、improvementCandidate 等）。

更根本的是：钱包体系（Wallet / WalletLedger / RechargeOrder / ReferralCode）压根没有 tenantId 列，只按 userId @unique——租户边界在资金相关表上是不存在的。

注意：这些点是否真的可被利用，取决于 handler 层有没有做归属校验，需要逐个接口实测才能定性。这里标 P0 是因为「没有兜底机制」这件事本身，而不是确认了可利用的越权。

④ CORS 配置过宽

server.ts:91 是 { origin: true, credentials: true }——反射任意 Origin 且允许携带凭证。等价于对任意站点开放带 Cookie 的跨域读。生产应立即收敛为显式白名单，这是本次评审里改动成本最低、收益最高的一条（一行配置）。

四、P1：近期必须收敛的

⑤ 计费两套语义并存

SKILL_PPU 目前硬编码在代码里且有两处真相源，应外移到 DB / 配置
图 3 · 两套计费语义并存

⑥ 鉴权靠 257 处内联调用，没有强制约束

resolveRequestContext(...) 在 48 个文件里被调用 257 次，全部是「每个 handler 第一行手写」。这意味着新增接口忘记写这一行 = 该接口无鉴权，而且当前没有 lint、没有测试能发现。正确做法是挂一个全局/作用域级 preHandler 把 context 注入 request，让「忘了写」在物理上不可能发生。

另外 requireAdminToken / requireOpsToken 有「非 production 且未配 token 就放行」的分支——如果生产误设了 NODE_ENV，后台就是裸奔的。建议改为显式开关而非靠 NODE_ENV 推断。

⑦ 知识库全文检索 = 全表扫描

knowledge-base.ts:985 的搜索落到 content: { contains: q }，对 @db.Text 大字段做前后模糊匹配，b-tree 索引完全失效；transcript 分支更是拼了 8 个 OR contains。全仓 零 FTS 定义（无 tsvector / GIN / pg_trgm）。知识库是会被持续灌数据的表，这条会随数据量线性恶化。

⑧ 前端没有请求层

lib/api.ts 只有 61 行，本质是个 URL 拼接工具。全前端 336 处裸 fetch( 散在 73 个文件里，authHeaders() 被复制 20 份、readJson() 被复制 15 份。没有超时、没有重试、没有 401 全局跳登录、没有取消。

⑩ 事务与连接池全部走默认值

64 处 $transaction，没有一处设置 maxWait / timeout，全部走 Prisma 默认 5 秒。而 billing-effects.ts 的事务体有 199 行、chat-persistence.ts 有 6,325 字符——高峰期锁竞争下会集中报 P2028。同时 DATABASE_URL 和 datasource 都没配 connection_limit / pool_timeout，多实例部署时容易打满 PG 连接。

七、结论

这套系统不缺功能，缺的是承载功能的框架。团队在「钱」和「身份」这两条最容易出事的线上投入了明显高于平均水平的工程严谨度——预留式计费、幂等键、fail-closed 的身份解析、常量时间比对、Serializable 隔离——这说明不是能力问题，是这些标准没有被推到全局。

因此我的建议不是「大重构」。先花 1～2 天做阶段 0 的止血，再用 1～2 周把横切关注点（请求、鉴权、错误、门禁）收敛成框架能力——这两步做完，新功能的边际成本会明显下降，后面拆巨型文件、上队列才有立足点。反之如果先去拆 3,748 行的 marketplace.ts，在没有测试、没有 CI 的情况下，大概率是拆完不敢上。

评审方式：静态代码勘察（4 路并行）+ 关键项命令行实测复核。所有 P0/P1 结论均已用 grep / 文件系统核对过原始证据，未采信未经复核的推断。
本报告未修改任何源码、配置或数据库。
