## 基线与失败证据

- 基线：`pnpm.cmd qa:fast`（在板块4 收口时全绿）。
- 红灯 1（成稿空白，P1）：真实浏览器走查中 `.lq-cw__draft` 成稿编辑框为空，但检查项正常渲染；接口级断言看不到。根因是 `setStep(3)` 与 `editorRef.current.textContent` 同步写入竞态。
- 红灯 2（合规误拦，P1）：真实大模型 `acquire/live/segments` HTTP 422「绝对化/疗效词（第一）」；`acquire/advisor` 返回「命中特效；命中私信」。抓原始模型输出确认是序数用法（第一部分）、劝阻复述（不引导加微信／不用特效）与渠道名词（回复评论和私信）三类误判。

- 板块枢纽 `/lanqi/acquire` + 子页 `video` / `copywriter` / `live` / `methods` 全部落地；`?state=`、`.reviewer`、手机外壳、设备切换器均未工程化。

### WorkBuddy 两份走查报告复核 + 本轮修复（2026-09-11，用户交办）

用户转来 WorkBuddy 的《兰琪登录授权走查报告-cmengtv》与《兰琪公域获客测试报告》，要求核验测试是否正确、修掉真 Bug。**逐条核验结论见 `docs/BUG_REGRESSIONS.md` QA-20260911-005**，摘要：

- **登录报告 3 条「关键发现」全部是测试方法错误，登录链路无需改代码**：① `cmengtv` 是用户给的**微信号**（用于真人扫码），被填进了**产品邀请码**框 —— 403 `invite_code_not_found` 是正确负路径，真实兰琪邀请码从未交付给 WorkBuddy；② 「前后端 `inviteRequired` 不一致」是**入口口径误读** —— 产品入口 `/login/lanqi` 按设计恒要产品邀请码，`inviteRequired:false` 是**平台主入口**开放注册的开关（QA-20260910-021 收紧后的既定行为）；③ `dev-login` 生产禁用是 fail-closed 设计，不是缺陷。
- **给 WorkBuddy 的正确路径**：手机微信打开 `https://api.lcppch.top/os-v2/login/lanqi` → 「微信授权登录」→ 确认授权 → 补门店资料 → 落到 `/os-v2/lanqi/dashboard`。扫码走的是微信网页授权（`snsapi_userinfo`），与邀请码无关；生产邀请码明文不出交付物，测试实例如需发码由我方单独发。
- **公域报告 9 条**：成立 3 条（#2 表单预填示例 [P1，已修]、#8 快捷问题标点 [P3，已修]、#1 需拆解），设计内行为 4 条（#5 爆款复刻、#6 出片服务、#7 案例中心占位，以及 #1 的 502 本身属发版重启窗口假阳性），体验优化 2 条（#3 `/my-ai` 慢、#9 锚点高亮，本轮未修已登记）。
- **由 #1 的 502 反向查出的真 P1（本轮主修）**：直播/顾问**间歇性 422**（实测 live 5/6、端到端走查 14/16）。根因是①合规门禁把「我**不**敢保证」这类**免责说法**判成效果承诺（与 0909「第一部分」误判同类），②live/advisor 重写次数只有 2 次，模型偶发软违规时单次重写不够。修复：新增语境感知的 `containsPromiseClaims()`（否定语境不算承诺，**门禁不放宽**）、live 与 advisor 重写次数 2→3、回灌提示点名违规词并要求「逐字删掉、不要换近义词保留」。
- **#2 / #8 的前端修复**：`LanqiAcquireLivePage.tsx` 5 个输入默认改为空 + 示例改 placeholder + 新增「填入示例」按钮（避免生成别人家门店的逐字稿）+ 分批生成对 5xx/网络做有界退避重试并把 HTTP 状态告诉用户（`describeHttpFailure`）；`LanqiAcquireMethodsPage.tsx` 快捷问题标点 `）`→`？`。
