# LQ-35 门店读取失败被说成「门店信息还在加载」（公域获客 文案十件套 / 视频获客）

状态：**开发中**（2026-09-18 建卡）。分支 `codex/lq35-store-gate`，独立 worktree。

## 归属

- 产品：兰琪美业经营增长智能体（公域获客 · 美业文案十件套 + 视频获客）
- 层级：产品专用（页面错误口径）；复用平台已有的门店可用性判定，不新增公共能力
- 风险：低（只改前端提示与门禁口径，不碰后端路由 / 鉴权 / 计费）
- 是否允许并行：允许（只碰 `apps/web/src/pages/LanqiAcquire*` 与一个契约冒烟脚本）

## 用户结果

老板打开「公域获客 → 美业文案十件套」，点生成却只看到「**门店信息还在加载，请稍后再试一次。**」——不管点几次都是这一句，看不出到底卡在哪、也不知道下一步做什么。修完之后：**能生成就正常生成；不能生成必须一次说清「为什么不能 + 去哪解决」**，绝不再用「还在加载」掩盖真实原因。

## 现象与取证（2026-09-18，全在生产只读完成）

1. **生产 nginx 访问日志**（`/var/log/nginx/access.log-20260918`，即 09-17 当天）：老板本人浏览器（`38.106.19.252`、`Chrome/144 … QuarkPC/7.2.0.992`）在 08:31:11 / 08:32:30 / 08:34:32 / 08:34:50 / 08:49:57 / 08:50:01 六次请求
   `GET /os-v2/api/lanqi/stores` → **403 / 175 字节**，referer 分别是 `/os-v2/lanqi/acquire/copy-kit`、`/os-v2/lanqi/moments/friend-circle`、`/os-v2/lanqi/moments/wechat-group`。
   同页面的 SPA 壳 `GET /os-v2/lanqi/acquire/copy-kit` 是 **200**——**页面能打开，只有门店接口被挡**。
2. **同一账号同一时段的其他接口正常**：`GET /os-v2/api/market/me 200`、`GET /os-v2/api/wallet 200`，说明登录态有效、租户存在，403 不是「没登录」。
3. **403 的 body 长度可以直接对号入座**：权益门禁（`apps/api/src/services/access-guards.ts`）的 403 响应体为
   `{"error":"product_entitlement_required","code":"<code>","message":"<22 个汉字>","trace_id":"req-x"}`。
   按 `reqId` 实测格式（服务端日志 `reqId":"req-7"`）逐段计长 = 10+28+10+27+13+**66**+14+5+2 = **175 字节**，与日志里的 `403 175` 完全一致；只有 `code` 为 `product_entitlement_missing`（未开通，27 字符）或 `product_entitlement_expired`（已到期，27 字符）时才是 175（`…_inactive` / `…_required` 是 28 字符 → 176）。**即：真实原因是「这个租户没有生效中的兰琪权益」，不是门店没读出来、也不是服务 500。**
4. **服务端日志佐证**：`journalctl -u baolu-os-v2` 对应时刻能看到同一批 `GET /lanqi/stores` 的 `incoming request`（`req-7` / `req-b` / `req-l` / `req-m` / `req-v` / `req-w`），不是网关直接拒绝、也没有 500。
5. **前端把真原因吞掉了**（两处，同一个写法）：
   - `apps/web/src/pages/LanqiAcquireCopyKitPage.tsx`：`fetch(...).then((r) => (r.ok ? r.json() : { stores: [] })).catch(() => setStores([]))` ——403 被当成「门店列表为空」；
   - `apps/web/src/pages/LanqiAcquireVideoPage.tsx`：`catch { /* 门店加载失败不阻断页面 */ }` 静默吞掉（页面级组件两处）。
   然后点生成时只给一句 `if (!storeId) { setError("门店信息还在加载，请稍后再试一次。") }`（`LanqiAcquireCopyKitPage.tsx` 1 处、`LanqiAcquireVideoPage.tsx` 2 处）——**把权限问题说成了加载问题**，老板只会一直重复点。

## 根因

兰琪所有路由注册在 `requireProductEntitlement("lanqi")` 作用域内（`apps/api/src/products/register.ts`），租户没有生效中的 `lanqi` 权益时整个 `/lanqi/*` 一律 **403**（含 `/lanqi/stores`）。前端却把「读门店失败」与「门店为空」合并成一个空数组，再用「门店信息还在加载」兜底提示，于是**权限 / 状态类失败被呈现成加载中**。

## 修复口径

复用仓库既有的唯一判定（LQ-20，`apps/web/src/lib/lanqi-store-gate.ts` + `use-lanqi-store-gate.ts` + `LanqiStoreGateBanner.tsx`，朋友圈获客两页已在用）：

- 门店读取失败时**保留后端 `code`**，按 `product_entitlement_missing / _expired / _inactive / forbidden / network` 分流文案与 CTA；
- 页面顶部渲染提示条（`data-lanqi-gate` / `data-lanqi-gate-reason`）；
- **删除** `!storeId` 时那句「门店信息还在加载，请稍后再试一次。」，改用判定给出的 `blockedReason`。

## 验收条件

1. 契约冒烟 `pnpm.cmd lanqi:acquire-ui-contract-smoke` 新增断言：两个页面都必须用 `useLanqiStoreGate` + `LanqiStoreGateBanner`，且**源码里不再出现**「门店信息还在加载」这句误导文案（先跑一次证明 FAIL，再实现到 PASS）。
2. `pnpm.cmd lanqi:store-gate-smoke`（纯函数判定）保持全绿：`entitlement_missing / expired / inactive / forbidden / network / empty / ready` 七种状态各有唯一文案与出口。
3. `pnpm.cmd typecheck` 通过；`pnpm.cmd qa:fast` exit 0。
4. 页面级行为：403 时页面出现提示条并显示准确原因（未开通 / 已到期 / 无权限 / 读取失败），**不出现**「还在加载」；门店可用时提示条不占版面、生成照常。
