# LQ-34 兰琪通用钱包打通（充值入口在兰琪、钱包与思潼 AI 通用）

状态：**开发中（未上线）**

## 用户口径（2026-09-16 老板拍板，逐条可追溯）

1. 「**兰琪的用户只使用兰琪智能体**，也就是说需要在兰琪智能体里充值；未来在兰琪智能体里加一个『更多智能体』的接口，点击之后进入思潼 AI，用户可以继续在思潼 AI 里使用其他智能体。**在兰琪智能体充值的积分，可以支持同时在思潼 AI 里使用其他智能体**。也就是说钱包是通用的。未来用户进入思潼 AI 之后，也可以在思潼 AI 充值。」
2. 多人门店的付费主体：**选选项 1** —— 「兰琪里不管谁操作，都扣**租户老板（owner）的钱包**，流水里记『谁操作的、扣的是老板的钱』；思潼 AI 侧保持『谁登录扣谁的钱包』。」
3. 迁移方式：**选 Phase 2（正式，不做双轨过渡）** —— 「把历史租户额度一次性迁进钱包（或按门店发一笔等额），下线回退分支，只留一本账；补对账报表和退款一致性。」
4. 「**不显示人民币消耗**，兰琪的积分计费逻辑和思潼 AI 保持一致。」

## 用户结果

门店老板在兰琪里充值后，**所有兰琪能力立刻可用**（图片 / 视频 / 爆款复刻 / 文案十件套 / 经营问答）；同一笔钱未来进思潼 AI 也能直接花；系统里**只有一本钱包账**，有可对账的流水（谁操作、扣谁的）。

## 实施计划（按顺序，每步都有验证）

### 1. 计费主体解析（本轮已开始）

- 新增 `apps/api/src/services/lanqi-wallet.ts`：按 `tenantId` 解析**租户 owner**，命中失败即 **fail closed**（`lanqi_wallet_owner_missing`，不扣费、不放行）。
- 统一收口三个动作：`precheckLanqiWallet`（余额校验）/ `chargeLanqiWallet`（扣费）/ `refundLanqiWallet`（退款）。
- 幂等与审计口径：
  - 幂等键统一为 `lanqi:{tenantId}:{requestId}`，避免不同门店共用同一 owner 时撞键；
  - 扣费走 `consumeWalletCredits`（paid → bonus、Serializable、条件更新、同键幂等）；
  - **退款按原扣费流水回退到原桶**（读该 requestId 的 consume 流水，paid/bonus 各退多少就退多少），调用方不用记账；
  - 操作人写进 `WalletLedger.source`（`lanqi:operator=<userId>`），付费人是 owner，二者分开可审计。

#### 已踩过的坑（避免重复）

- 钱包幂等键是 `(walletId, refRequestId, type)`：兰琪侧统一用 `lanqiWalletRequestId(tenantId, requestId)` 加租户前缀，否则同一 owner 服务多门店时会撞键。
- `refundWalletCredits` 要求 `breakdown: {paid, bonus}`；**不要自己记账**，用 `refundLanqiWallet`（它读原 consume 流水按桶退回）。
- `lanqi-wallet-smoke` 是库级回归，会建临时租户/用户/钱包并自动清理；本机 `.env` 指向 `localhost/sitong_os_v2`（dev 库），**不要**把它指向生产跑。

### 3. 历史额度一次性迁移（未做）

- 迁移对象：`CreditAccount.balance > 0` 的兰琪租户。
- 迁移目标：该租户 **owner 的钱包**，进 `paid` 桶（历史额度是购买 / 授予所得，不是营销赠送，不设到期）。
- 幂等与留痕：每租户一条 `WalletLedger`（`type=grant`、`source=lanqi_credit_migration:<tenantId>`、`refRequestId=lanqi-migrate:<tenantId>`），重复执行不重复发放；迁移前逐租户导出 CSV 备份，迁移后把 `creditAccount.balance` 置 0 并保留行（不删数据）。
- 回滚：备份 CSV + 「反迁移」脚本（把钱包里的额度扣回租户账户）。

### 4. 对账与退款一致性（未做）

- 出「充值订单 / 钱包流水 / 兰琪消费流水」三方对账口径，至少覆盖：充值、扣费、退款、迁移、推荐奖励。
- 退款规则只有一条：**原路退回钱包（原桶）**，且同一 requestId 只退一次。

## 本次不做

- 不做双轨过渡（用户已选 Phase 2）；不保留「钱包不足回退租户账户」的分支。
- 不改思潼 AI 侧「谁登录扣谁」的现状。

## 风险

- **钱的路由切换**：7 个扣费点必须一次性切干净，否则会出现「一半扣钱包、一半扣租户账户」的裂账；合并 / 发布需串行。
- 历史额度迁移不可逆（有 CSV 备份与反迁移脚本兜底）。
- 多人门店：员工操作扣老板钱包，必须在页面与流水里说清（避免员工以为花的是自己的）。
- `credit-reservations.ts` 目前是租户账户的预留 / 结算模型，切钱包时要一起改成「钱包扣费 + 原桶退款」，否则经营问答会出现半套逻辑。
