结论先行：一次性全问覆盖不全 → 推荐「智能预采集 + 生成后补全」混合方案（复用现有 precheck / interview-hints 能力）

!直接回答你的两个疑问

根因
不是"问得不够"，是输入粒度 vs 产出野心的结构性缺口。前端只收 6 个战略槽位，产出却要 80 选题 / 主页四件套 / 预算数字 / 门店数等运营细节；技能 prompt 红线又明文"未确认即标记【待补】"，模型按指令留白。
能一次覆盖全吗
不能，根本性做不到。缺口分两类：①可预见缺口（预算/团队/产品名/价格）能前置问但全问会毁体验；②发现型缺口（要你拍板的主页昵称、要你确认的话术钩子）——你没看到草稿根本不知道要补什么。
该怎么做
你设想的"先出草稿→按待补充反向提问→再生成"是更对的路。但纯两遍会每次白花 99 算力整包重跑，推荐折中：预采集（拦可预见缺口）+ 生成后补全（捞发现型缺口），且补全走"章节级 patch"而非整包重跑。

A为什么产出里总有「待补充」

诊断：6 个战略字段要喂饱一份需要 20+ 具体运营信息的全案 → 模型按红线留白。这不是"再问几个问题"能根治的。

C推荐方案 · 混合流程

D关键设计决策

  • 补问要"少而精"：pass② 只问 3–5 个最高价值运营问题（预算量级 / 团队配置 / 最硬产品 / 主推价格带 / 想主打渠道），别贪多。
  • 补全走章节级 patch，不是整包重跑：前端已有"单章复制"，后端加一个 patch 接口——只把用户补答喂给对应章节重生成，省下整份 99 算力。发现型缺口（主页昵称等）本就可单章解决。
  • "待补充"反过来变成产品亮点：把首稿的【待补】聚类成一张"补全清单"卡片，用户逐条勾填，体验从"一堆洞"变成"你来拍板"，比硬塞问卷友好得多。
  • 可预见 vs 发现型分层处理：可预见的在 pass② 拦，发现型的交给 pass④；两者叠加后首稿待补量可降 70%+，残余再让用户拍板。

风险：章节 patch 需保证其他章不被"带跑偏"——patch 时把原全案作为上下文基线上锁，只换目标章。这是实现时第一个要验证的点。
