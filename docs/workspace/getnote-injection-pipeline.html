⚠️ 关键纠正：结构化 1280/422/26 没有直接被注入

metadata.analysis（你存的 coreViews / quotes / overview 三段 JSON）在整条注入链路里完全没被读取。 buildKnowledgeEvidencePack 的类型签名只有 {id, title, content}，metadata 连参数都不是。

但 1280/422/26 的原始文字确实进了上下文——因为 document.content 存的就是 Get笔记 note/list 返回的完整智能总结原文（getnote-summary-sync.ts:3-4 明确写"含金句精选/章节概要/录音总结"）。 parser 只是把同一段文本解析成 JSON 计数，原文仍留在 content 里。所以 LLM 看到的是被压缩后的原始 markdown 文本， 不是精确的"核心观点：XX"结构化字段。

✅ 一道硬门槛：不是所有 99 篇都能进上下文

loadAutomaticKnowledgeDocuments（knowledge-base.ts:1245-1256）的筛选条件：

  • 必须绑定到某个 subjectId（没挂主体的文档进不来）
  • usagePolicy === "auto"（"recommend" 的不自动带入）
  • confirmedAt !== null（未确认的草稿不带入）
  • sensitivity !== "sensitive"（敏感资料排除）
  • 最多 20 篇，按 occurredAt desc 取最新
  • 总字符预算 16000，单篇 520~2200，超出按信号词抽取

→ 你存的 99 篇里，实际能自动注入对话的，取决于"已挂主体 + auto + 已确认 + 非敏感"的数量，且封顶 20 篇 / 16000 字符。 第 ②③ 消费方（数字员工 / 美业选题）同样受这套条件约束。

你以为的实际发生的
1280/422/26 作为结构化结论被精准喂给 LLM 结构化 JSON 没被读；原始总结文本被压缩后混入首条 user 消息
23 篇无 analysis 的缺口 → 模型看不到内容 这 23 篇只要 content 有、且过筛选，照样能带入（缺失的只是结构化计数，非正文）

🔧 真正可优化的缺口

既然 metadata.analysis 已解析好却被 buildKnowledgeEvidencePack 无视，最划算的改进是： 在该函数里优先用 analysis 的结构化字段（overview / coreViews / quotes）拼证据包， 而不是退回读整段 content。好处：① 结论密度更高、更精准命中 query；② 16000 字符预算能塞进更多篇的"真结论"； ③ 那 23 篇无 analysis 的回落到 content，无缝兜底。这一改能让 1280/422/26 从"藏在原文里"变成"被精准引用"。
