供你核对正确性。本次按你的口径修正：getnote 来源、同步时间范围 30 天、进页面先远端预检待同步数、点击同步才拉取落库；正式版只翻 note/list 取免费智能总结，分析阶段 0 次 LLM。

主流程（自上而下）

分析阶段：为什么不再调 LLM（正式版关键改动）

  • 旧流程（已废弃）：pullGetNoteTranscripts 逐条调 note/detail（每篇一次请求，限流重）→ 取逐字稿前 6000 字硬喂 DeepSeek。浪费钱，且长录音干货被截断；92 篇 ≈ 92 次 LLM。
  • 新流程（当前）：syncGetNoteSummaries 只翻 note/list（每页一次请求，约 10 次）→ GetNote 的 content 自带免费智能总结（#### 录音总结 / ### ✨ 金句精选 / ### 📅 章节概要）→ parseGetNoteSummary 切成 metadata.analysis（coreViews / quotes / chapters）→ 0 次 LLM。
  • 历史笔记回填：旧库文档若缺 metadata.analysis，persist 的 unchanged 分支会回写本次解析成果；窗口外的旧笔记则在分析阶段整体跳过（不再调 LLM，保留原始 content） → needsAnalysis = 0，根治"整理笔记要点 0/92 很慢"。
  • 空判定与 note_type 解耦：实测 note_type 不止录音（recorder_audio / audio / class_audio / link / plain_text），空笔记判据改为「解析产物是否非空」兜底（录音卡 / 空白语音 / 时长 0 秒 / 标题关键词），不再误判。
  • 19 位 ID 精度修复：雪花 ID 超 Number.MAX_SAFE_INTEGER，解析前转字符串，避免拿错 id 导致空数据（"未命名笔记 0 字"）。
  • tags 用于分类：type=ai 业务标签（美业/短视频运营/视频号运营…）价值高，作一级分类；type=system（录音卡笔记）丢弃。
可观测性：/tmp/getnote-summary-sync.log 记录 SYNC_START → LIST_OK → NOTE_OK → SYNC_DONE，且 detailRequests=0；getnote-summary-sync.ts 加载时有 MODULE_LOADED 日志，用于确认后端已用新代码重启。
